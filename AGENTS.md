# Drop

A Mac app that installs an app straight out of a `.dmg` without mounting it, and offers to when a new DMG lands in Downloads. GPL-3.0. Plan, decisions and the design canvas link live in the Nidus Labs workspace (`plans/drop.md`), not in this repo. Research, benchmarks and the sample DMGs: `.claude/` (gitignored).

## Layout

A Swift package (`Package.swift`), no Xcode project yet:

- `ReaderCore`: shared types (`BlockDevice`, `FileSystem`, `Entry`, `Extent`, `ByteReader`, `ReaderError`).
- `DiskImage`: UDIF container, decoders, partition maps.
- `HFSPlus`, `APFS`: read-only filesystems over a `BlockDevice`.
- `DMGReader`: opens a `.dmg` and returns its filesystem. `dmg-inspect`: a CLI over it.
- `Extractor`: stages an app out of a `FileSystem` (4 workers, POSIX writes, xattrs, quarantine with the do-not-translocate flag) and installs it by rename or atomic swap.
- `Mounter`: the hidden-mount fallback for images the readers can't handle (encrypted, sparse, unknown compression, decmpfs). `HiddenMount` attaches with `diskutil image attach --readOnly --nobrowse` at a 0700 folder under `$TMPDIR/dev.niduslabs.drop.mounts`, detaches by device node (`diskutil eject`, then `force`), and `sweepLeftoverMounts()` clears that folder after a crash. `MountedFileSystem` reads the volume as a `FileSystem` (POSIX, never following symlinks) so the Extractor stages from it unchanged. Measurements and licence behaviour: `.claude/research/hidden-mount.md`.
- `Verifier`: signing info, strict validation, Gatekeeper assessment, the `Verdict` the panel shows, same-developer check, and stapling a DMG's ticket into an app. Use the `async` overloads from tasks; the sync ones stall under Swift concurrency.
- `Installer`: `InstallSession`, the actor the app drives per DMG: reading → licence → (password, hidden mount) → identified (name, version and icon read at user-initiated priority, before the size walk) → background staging and check → ready/warning/refused → install. The hidden mount is detached as soon as the app is staged, and on cancel or failure. States in `InstallState.swift`. In Low Power Mode or at a serious thermal state it waits in `waitingToPrepare` (`StagingConditions`, injectable). Install boosts staging, its calling thread and the signature check (cancelled and reissued at user-initiated).
- `Onboarding`: first-launch onboarding's state machine (`OnboardingCoordinator`), with the folder access, default handler and login item behind protocols so `OnboardingTests` drive it with fakes. Rules below.
- `DropApp` (product `Drop`): the background app, AppKit + SwiftUI, with no Dock or menu bar icon. `AppDelegate` (lifecycle, launch sweeps, login item via `SMAppService.mainApp`, Open With, onboarding), `OnboardingView` (the five pages and the window, 600 × 540, one bottom-anchored rhythm in `Theme.Onboarding.Rhythm`: the art panel takes whatever height the text and buttons leave; floating while open), `WindowPresence` (the activation policy: regular while Settings, the install window or onboarding is open, accessory when the last closes, never for the popup; and how windows come forward, including `--background-test`) and `OnboardingServices` (the live requests and the test-launch stand-ins), `DownloadsWatcher` (FSEvents on one folder, 0.1 s latency, NoDefer; a rename into a `.dmg` name is finished at once, a file that appears without one waits `Theme.Timing.stableSize` at the same size; attribute-only events are ignored), `InstallController` (one `InstallSession` per DMG, a queue, one panel at a time, shown at once with "Reading…", handled files in `~/Library/Application Support/Drop/handled.json`), `PanelWindow` (the popup: a non-activating `NSPanel` at the top right of `NSScreen.main`, sliding in on our own spring; and the centred window an opened image gets, which activates Drop), `Boards.swift` (one view per design board, shared by both; the Update board's running-app note says only what is true at each step: open, quit, didn't quit (amber), updated (the moss info callout), and keeps the height of the tallest), `SelfImage` (Drop's own disk image, by bundle ID: the running one's, or the release or debug ID for either build. Never Install or Quit and Update: newer by `CFBundleShortVersionString` then `CFBundleVersion` gets Check for Updates, which closes and runs `UpdateCheck`, Settings' check, logging only where no updater runs; the same or older gets Done. The session stops once the app is identified, so nothing is staged; tested in `SelfImageTests`), `PanelButtons` (what the primary, secondary and link show in each state for both surfaces, a pure value tested in `PanelButtonsTests`: one capsule whose label changes in place, from Install or Quit and Update through "Quitting …" and "Updating … N%" to Open), `QuitAndUpdate` (`QuitThenInstall`: one press asks the running copy to quit, never forces, waits up to `Theme.Timing.quitTimeout`, then installs; `RunningApp` is injected so `QuitThenInstallTests` use fakes), `AfterInstall` (what happens once installed: stay on Installed, reopen a copy that was quit, or with "Open the app when it's installed" hold, close the surface, then open the app; tested in `AfterInstallTests`), `SettingsView` (groups Watching, Installing, General, Drop; pausing is the Ask switch; Quit Drop at the bottom), `MainMenu` (the standard app, File, Edit and Window menus, so ⌘W, ⌘Q and paste work in this `LSUIElement` app; shown in the menu bar only while Drop is regular), `Latency.swift` (popup, summary, icon, size and verified milestones as `latency` logs; `.claude/research/summary-latency.md`), `DiskImageHandler` (Open With and the "Open disk images with Drop" default; "Open disk image" always uses DiskImageMounter by name). The Nidus component kit (`Components.dc.html`) is `Controls.swift` (button, switch, field and card styles on real controls, Tab-focusable even with macOS Keyboard navigation off) and `Select.swift` (`NidusSelect`: its own menu in a child panel, never `NSMenu`; `--demo select-settings|main|window[-hover|-key]` opens it, `.claude/checks/select-shot.sh` captures it over a striped backdrop); motion after Purge is `Motion.swift`; Manrope for onboarding headings and the byline is `Typeface.swift` (bundled from `Resources/Fonts`, OFL). Sizes, colours (dynamic, with Increase Contrast variants) and motion values: `Theme.swift` (including the quitting shimmer, `Theme.Motion.shimmer*`, and the close before an app opens, `installedHold`, `windowExit*`, `popupExitDuration`). `Demo.swift` is debug-only. `Updates/`: Sparkle with Drop's own surfaces (Releasing, below).
- `drop-impact`: the background-impact benchmark's load and staging processes, run by `.claude/research/scripts/impact_bench.py` (results in `.claude/research/impact-bench.md`).

## Commands

Homebrew's LLVM env breaks Xcode builds, so build through `scripts/swift.sh`, which clears it:

```sh
scripts/swift.sh build
scripts/swift.sh test                 # unit tests; fixtures first: scripts/fixtures-*.sh (installer and mount after verifier)
DROP_TIMING=1 scripts/swift.sh test --filter MountFallbackTimingTests   # hidden mount vs direct path
scripts/corpus.sh                     # also the 34 real DMGs in .claude/samples/ (makes and deletes 4.4 GB of reference copies)
scripts/swift.sh run dmg-inspect <file.dmg> [--tree]
scripts/build-app.sh [--debug]        # .build/Drop.app: release (or debug: `dev.niduslabs.drop.debug`, "Drop (Debug)") build, Info.plist, Sparkle.framework, ad hoc signature
                                      # env: VERSION (1.0.0), BUILD (= VERSION), SIGN_IDENTITY (-), SPARKLE_PUBLIC_KEY (release key)
```

**Running the app for tests.** Never against the real Downloads, Applications or Trash, and never in the foreground: add `--background-test` (every `--demo` is one already). It never activates Drop, makes a window key or changes the activation policy; windows order in behind the user's at the normal level, Open Documents events skip AppKit's handler (which activates), and the copy ignores "show Settings" from other launches. Capture with `screencapture -l <id>` (works occluded) and drive by PID through the accessibility API (`.claude/checks/drive.swift`). Debug builds have their own bundle ID, so they never meet an installed release copy in the single-instance check, Launch Services or the "show Settings" notification (named after the bundle ID). `.claude/checks/e2e-v3.sh` runs the whole background check on a debug copy. Pure app logic (activation policy, onboarding rhythm) is tested in `DropAppTests` through `@testable import DropApp`.

```sh
S=$PWD/.build/app-check/run; mkdir -p $S/watch $S/dest $S/trash
.build/Drop.app/Contents/MacOS/Drop --background-test --watch $S/watch --destination $S/dest --trash $S/trash &   # any of these skips the login item; not `open`, which can reach another running Drop
cp .build/fixtures/installer/one-app.dmg $S/watch/                                     # panel appears
.build/Drop.app/Contents/MacOS/Drop --demo <state> --appearance dark                   # debug build only; prints DEMO_WINDOW <id>
.claude/checks/app-demo.sh <state> <light|dark> out.png                                # screenshot one state
```

Demo states are listed in `Demo.swift` (onboarding pages: `onboarding-1` … `onboarding-5`, `onboarding-2-denied`, which `.claude/checks/onboarding-shots.sh` shoots; `window` is board 1 in the centred window; `open-after[-fail]` and `window-open-after[-fail]` play an install through the close before the app opens; `update-flow[-timeout]` and `window-update-flow[-timeout]` play Quit and Update from one press, and `done-update` is its done state; `self-newer`, `self-same` and their `window-` forms are Drop's own disk image, shot with `.claude/checks/self-shots.sh <binary>`; the four flows print `DEMO_STEP <name> <frame>` at each step). `.claude/checks/insets.sh <state>` and `.claude/checks/contrast.sh <state> <look>` measure insets and text contrast from the accessibility tree. `.claude/checks/e2e-popup.sh` runs a release test copy through the popup, install and centred window by PID; `focus-walk.swift` prints the Tab order from the accessibility tree, `onboarding-flow.swift` checks the Command-Tab policy, `popup-latency.swift` times download-to-popup. Quit a test copy by its PID. A second launch of Drop (Finder, Spotlight) asks the running one to show Settings and exits, even from another path (`~/Applications` beside `/Applications`), so only one copy watches Downloads; release-ID test copies inside `.build` stay apart (they never make an installed copy quit, and a `.build` launch defers only to a copy at its own path; `SingleInstance`, tested in `SingleInstanceTests`); demo and `--watch`/`--destination`/`--trash` launches are exempt, so they run beside a copy that watches the real Downloads and never poke it. `agent-desktop --app Drop` can match that other copy: target a test copy by PID or `--window-id`.

## Onboarding

Shown on first launch, before Drop touches the watched folder, the default handler or the login item; each is requested only by its page's button (Allow Downloads, Use Drop, Start at Login). State is one JSON value under `onboarding` in the preferences domain (the test domain `dev.niduslabs.drop.test` in test launches):

- **Shows at launch** until Done, or until it's closed early (Esc, close button) after Drop got access to the watched folder. Closed early without access records `reshowReason: folderAccessNotGranted` and returns next launch at the Downloads page: Drop can't work without it and never asks by itself. Closing on the last page counts as Done.
- **The watcher starts** once access is granted (the first listing succeeds) or another folder is chosen, or once onboarding is done (after Continue anyway macOS doesn't ask again).
- **"Open Drop at login" is off by default**; only Start at Login or the Settings switch turns it on. A registration failure is logged and onboarding moves on.
- Opening Drop while onboarding is open brings onboarding forward instead of Settings.
- **Test launches:** `--watch`/`--destination`/`--trash` skip onboarding so scripted panel checks see the panel at once. `--reset-onboarding` (debug) clears the test domain's state and shows it; relaunch with `--no-login-item` to see the relaunch rules. In test launches the login item and default handler are stand-ins that only log, and Allow Downloads lists the folder only when it's a `--watch` folder; without one it reports denied and never touches `~/Downloads`.

## Conventions

- **Insets are theme tokens:** `Theme.panelInset` (18, all four sides of the popup; left, right and bottom of the centred window, whose top is the title bar) and `Theme.onboardingInset` (24, left, right and bottom of onboarding). No view adds its own outer padding on top.
- **Controls come from the kit** (`Controls.swift`): `.nidusPrimary`, `.nidusSecondary`, `.nidusSmall`, `.nidusLink()`, `.nidusSwitch` (no checkboxes anywhere), `NidusSelect`, `.nidusField`, `InfoCard`/`Callout` kinds (neutral, moss info, amber warn, red error). Text colours clear 4.5:1 on rendered pixels in light and dark; measurements in `.claude/screens/app-v2/measurements.md`. Every animation reads Reduce Motion.
- **Format and lint with Apple's `swift format`** (ships with Xcode, nothing to install or pin), configured by `.swift-format`: `swift format --in-place --recursive Sources Tests Package.swift`, then `swift format lint --strict --recursive Sources Tests Package.swift`. Decided 2026-11-16 over SwiftFormat and SwiftLint.
- **Every on-disk read is bounds-checked** through `ByteReader`; a corrupt image throws `ReaderError.corrupt`, never crashes or hangs.
- **Images are untrusted input.** Tests never mount, except through `HiddenMount` in `MounterTests` and the installer's mount-fallback tests: only the fixtures from `scripts/fixtures-mount.sh` (and samples in opt-in runs), read-only, under a test-only root, each checked to leave nothing attached. Scripts that mount use `hdiutil attach -nobrowse -noautoopen -mountrandom` and detach by device node: `-readonly` for anything downloaded; read-write only for a fixture image the script just created itself (to add compressed, fragmented or case-only files hdiutil won't copy).
- **One package dependency: Sparkle**, pinned `exact:` in `Package.swift` (2.10.1, 2026-11-17). Upgrading is a deliberate change: read its changelog, check `UpdateDriver` against `SPUUserDriver`, and rerun `.claude/checks/update-e2e.sh`. Everything else is system libraries (libz, libbz2, Compression).
- **The app icon comes from the assets repo** (`../assets/apps/drop/`, generated there). Refresh the committed copy with `scripts/sync-icon.sh`; never edit `Resources/AppIcon.icns` by hand.

## Releasing

Releases are Developer ID signed, notarized and stapled DMGs on GitHub Releases, built only by `.github/workflows/release.yml`; nothing is signed or notarized from a laptop.

**Cut a release:**

1. Add a `## X.Y.Z` section to `RELEASE_NOTES.md`: short "- " lines, one change each. The first three show in the update popup.
2. Tag and push: `git tag vX.Y.Z && git push origin vX.Y.Z`. Or run Actions › Release with a version (it tags the current commit).
3. The `release` environment holds the job; with required reviewers set, approve it there.
4. The workflow builds with `VERSION=BUILD=X.Y.Z`, signs inside out (Sparkle's `Autoupdate`, `Updater.app`, the framework, then the app; hardened runtime, timestamp), builds `Drop-X.Y.Z.dmg` (the app plus an Applications link, `hdiutil`, signed), notarizes it (`notarytool --wait`), staples and `spctl`-assesses it, signs it with Sparkle's `sign_update`, writes `appcast.xml` (`scripts/appcast.sh`) and publishes both as the latest release.

**Secrets** (repo secrets; never printed, never on disk longer than one step):

| Secret | What |
|---|---|
| `DEVELOPER_ID_P12`, `DEVELOPER_ID_P12_PASSWORD` | base64 PKCS#12 with only "Developer ID Application: Jatin Kumar (2M54BB9U46)" and its key. Imported into a throwaway keychain with a random password, deleted in an `always()` step |
| `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_PRIVATE_KEY` | App Store Connect API key for `notarytool`; the `.p8` is written to `RUNNER_TEMP` and removed when the step ends |
| `SPARKLE_ED_PRIVATE_KEY` | Sparkle's EdDSA private key: base64 of the 32-byte Ed25519 seed, the format `sign_update --ed-key-file` reads. Passed on stdin (`--ed-key-file -`). Generated with `openssl genpkey` (never the keychain); its public half is `SUPublicEDKey` in `scripts/build-app.sh`. Backed up in the workspace `creds/` as `DROP_SPARKLE_ED_PRIVATE_KEY.txt` (and `DROP_SPARKLE_ED_PUBLIC_KEY.txt`). **Key rotation (2026-11-17):** 1.0.0 trusts the first key, which has no copy outside this secret. 1.0.1 ships the new public key but must be signed with the old one, so the secret is swapped only after 1.0.1 is published: `gh secret set SPARKLE_ED_PRIVATE_KEY -R niduslabs-dev/drop < ../creds/DROP_SPARKLE_ED_PRIVATE_KEY.txt`. Sparkle accepts a new key only through an update signed with the old key or the same Developer ID, so never change the key and the Developer ID in the same release |

**How updates flow:** each install reads `releases/latest/download/appcast.xml` (`SUFeedURL`) once a day. Sparkle downloads the DMG in the background, checks its EdDSA signature against `SUPublicEDKey` and the app's code signature, and `UpdateDriver` shows Drop's popup ("Drop X is ready"; Restart to Update or Later). Later installs on quit and keeps the banner in Settings. With Install updates automatically off, the popup asks first (Download). Failures are logged (`log stream --predicate 'subsystem == "dev.niduslabs.drop" && category == "updates"'`), never shown; the next daily check retries. Sparkle's own windows never appear. No XPC services or `SUEnableInstallerLauncherService`: those are for sandboxed apps, so `build-app.sh` removes them. Ad hoc builds sign the app with `disable-library-validation` so it can load the ad hoc framework; Developer ID builds don't need it.

**Updates in debug and test launches:** off. Debug builds have their own bundle ID and never start Sparkle unless given `--update-feed <url>`. `.claude/checks/update-e2e.sh` runs the real path with a throwaway key: a fake 0.9.1 in a signed DMG, a localhost appcast, a 1.0.0 copy that shows the popup, then install on quit. Demo states: `update-ready`, `update-available`, `update-ready-plain`, `settings-update[-bottom]`, `settings-update-idle[-bottom]`; shots in `.claude/screens/updates/`.

**CI** (`.github/workflows/ci.yml`, every push to main and pull request, no secrets): lint, build, fixtures, tests, then `build-app.sh` and `codesign --verify`. Tests that read the real sample apps (kept out of git) are listed in `.github/ci-skip-tests.txt`; add to it only for that reason. Both workflows run on GitHub's `xcode-27` image and pin every action to a commit SHA.
